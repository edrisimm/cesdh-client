OverviewThe five-stage data lifecycle

raw_input_data (original BFS + SOLKAT) | v input_clean_data (cleaned, filtered) | v regionalization/all_pckls (time-series per region) | v grid_planning_results (expansion + costs) | v grid_planning_publication/ figures (PNG charts)

Each phase depends on the previous one. The dataset IDs returned by uploads become the derived_from parents of the next phase.

  • 2Title — human-readable display name.
  • 3Owner — who is responsible for this repository.
  • 4Click Create to provision the repository. If it already exists, it will be reused.

Phase 1Upload raw_input_data/ — the root nodes

Click "Upload dataset" in the right drawer. Upload the two original source files: the BFS building register and the SOLKAT solar-potential intersection.

  • 1Drag and drop the file or click to browse.
  • 2Set Folder to raw_input_data so files land in the correct storage subpath.
  • 3Fill in Title, Owner, and Description.
  • 4Add Domain tags for discoverability.

No lineage yet

These are root nodes — they have no parents. Skip the Provenance section entirely. The dataset IDs returned after upload will be needed in Phase 2.

Phase 2Upload input_clean_data/ — first lineage links

Upload three cleaned CSVs. Two have a parent via the Provenance section. This is where PROV-O lineage begins.

  • 1Select Derived from — pick the raw BFS dataset from the dropdown. This creates a prov:wasDerivedFrom edge.
  • 2Enter a Run ID: clean_2024-04-30. This groups all cleaning outputs under a single PROV-O Activity.
  • 3Repeat for input_PV_HAK_EGID.csv (derived from raw SOLKAT) with the same Run ID.

input_scenarios.csv has no parent

Hand-curated file — leave Provenance empty. Not every file needs lineage.

Phase 3Upload regionalization/all_pckls/ — 3 inputs, 1 run

Upload each .pckl file. All three cleaned inputs are selected as parents. All share the run ID regionalize_2024-04-30.

  • 1Select all three cleaned datasets in the "Derived from" multiselect — regionalization consumes all of them together.
  • 2Set Run ID to regionalize_2024-04-30 — this groups the many pckl outputs under a single PROV-O Activity.

Repeat for every .pckl file

Upload one file at a time. Keep the same Derived from selection and Run ID for each. The hub records "3 inputs → 1 run → many outputs" as a single queryable activity.

Save every dataset_id from the upload confirmations — Phase 4 needs all of them as parents.

Phase 6 — AuditTrace lineage — "where did this come from?"

Click the 🧬 Lineage button on any dataset card, or switch to the Lineage tab. The Focused sub-view shows ancestors and descendants.

  • 1Focused mode — shows the lineage table for the selected dataset.
  • 2Each row shows the relationship (self, ancestor, descendant), title, folder, and run ID.
  • 3Click any ancestor to re-focus and explore its own lineage chain.

The acceptance test

If the ancestors column is populated, the provisioning worked. If empty, a derived_from was missed at upload time.

Phase 6 — AuditPipeline view — the whole activity graph

Switch to the Pipeline sub-view. This renders every prov:wasDerivedFrom edge as a flow diagram, color-coded by lifecycle stage.

  • 1Pipeline tab — shows the complete derivation graph.
  • 2Nodes are colored by folder (stage). Large clusters (e.g. 45 pckl files) are collapsed into group nodes.
  • 3Arrows show the flow from raw inputs → cleaned → regionalized → results → figures.

The complete lineage at a glance

If edges span all five stages, the provisioning is complete. A missing edge means a derived_from was missed.

TeardownCleanup — delete the repository

To wipe the demo state, open the Working in a Repository tab and use the repository management controls.

  • 1Type the repository name to confirm. This prevents accidental deletion.
  • 2Click Delete repository. This is irreversible — it removes all files, metadata, and version history.

What gets deleted

All LakeFS branches and commits. All physical files in MinIO. All RDF metadata in Fuseki. Everything.

ReferencePROV-O lineage fields in the upload dialog

These two fields in the upload dialog are what make lineage work. Without them, the hub stores files but cannot answer "where did this come from?".

Derived from

The multiselect field in the Provenance section of the upload dialog.

MeaningThis dataset was produced from these parent datasets (prov:wasDerivedFrom)
Used inPhases 2, 3, 4, 5 — any output that has inputs
Skip whenPhase 1 (raw) or hand-curated files with no parent

Run ID

The text input below "Derived from" in the upload dialog.

MeaningGroups uploads under one PROV-O Activity — "all outputs from the same processing step"
Used inEvery phase with a processing step (cleaning, regionalization, grid planning, publication)
Run IDs used in this example
PhaseRun ID# Parents
Phase 1 — Raw—0 (root)
Phase 2 — Cleanclean_2024-04-301 each
Phase 3 — Pcklregionalize_2024-04-303
Phase 4 — Gridgrid_planning_2024-04-30all pckls
Phase 5 — Figurespublication_2024-04-302

The four Run ID values are the most semantically meaningful: they group datasets produced by the same activity.

What the team gains

1. A single source of truth

Every file related to a planning cycle lives in one repository, one branch, one URL.

2. A reproducible chain of custody

A figure uploaded today is queryable all the way back to its raw input, even months later and even by someone who was not there.

3. A repeatable bootstrap

When the next planning cycle starts (e.g. 2025-04-30), repeat the same steps with updated files and run IDs. The new cycle lives alongside the old one.

That is the provisioning: not the computation of the grid plan, but the act of putting every artifact of the plan into a governed, queryable, lineage-aware home.
